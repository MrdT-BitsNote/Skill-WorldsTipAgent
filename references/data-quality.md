# 数据质量、清洗与降级规则（data-quality）

> 本文所有统计数字来自 2026-11-04 对线上两个数据集的**全量实跑**，不是估计值。
> v0.1.1 追加了四标准自检发现的 3 类缺陷及 A/B 对照结论，见 §6。
> v0.1.2 追加了全维度数据体检（7 维 POI、脏数据、重复、缓存新鲜度），见 §7。

## 1. 脏数据实测：`food[]` 混入非餐饮 POI

对 fun 全量 389 城 `food[]` 的 `type` 首段做统计：

| 主类 | 条数 | 处置 |
|---|---:|---|
| 餐饮服务 | 30244 | ✅ 保留 |
| 购物服务 | 290 | ❌ 剔除 |
| 住宿服务 | 164 | ❌ 剔除 |
| 体育休闲服务 | 157 | ❌ 剔除 |
| 生活服务 | 55 | ❌ 剔除 |
| 公司企业 | 35 | ❌ 剔除 |
| 商务住宅 | 33 | ❌ 剔除 |
| 风景名胜 | 17 | ❌ 剔除 |
| 地名地址信息 | 10 | ❌ 剔除 |
| 其他（科教/医疗/汽车） | 14 | ❌ 剔除 |

**典型案例**：`常德市.food[0] = 瑞高酒店`，其 `type = 住宿服务;宾馆酒店;五星级宾馆/餐饮服务;中餐厅;中餐厅`。
字符串中虽然包含「餐饮服务」，但**首段是住宿服务**——这是地图服务多段类型串里附带的酒店内餐厅信息，不代表该 POI 是餐馆。
原型曾直接取 `food[0]` 输出「瑞高酒店」作为美食 TOP1，属实错误。

**清洗规则（唯一权威）**：`type.split(';')[0].strip() == '餐饮服务'`。
不得改用 `in` 子串判断（会把酒店内餐厅放进来）；不得按 `mark` 或名称关键词猜。
清洗后按 `rating` 降序、`name` 升序稳定排序，保证同输入同输出。

| `cascade`（真实路径） | 360 | **0** | **0** | 31 | 再加 24 直辖市降级；391 个三元组全部有明确处置 |

> **口径说明**：v0.1.0 报告写「386 城市名 → 356 匹配 / 0 未匹配 / 30 省级」，是按城市名去重统计；

### 长途环线识别（实测）

湖南省数据包中 `citySlug == 'loops'` 的路线共 2 条，其 `city` 均为 `湖南`、`cs` 均为 `computed`。
即：**`city` 是省名而非城市名**，这是设计行为，不是脏数据。

**关键反例（v0.1.1 自检发现）**：全量数据里还有 **4 个「省名 / 直辖市名但非 loops」**的真实路线——
`北京`/`北京市`、`上海`/`上海市`、`天津`/`天津市`、`吉林`/`吉林省`。
旧版按「省份名前缀」猜环线，会把这 4 条误判成省级汇总；`cmd_city` 因此**明明有「北京市」档案却回报「无单城档案」**。
现改为只认 `citySlug` 派生的显式 `is_loop` 信号。

## 3. 分级匹配链（`match_city` 唯一权威实现）

```
0  province    is_loop=True（由 citySlug=loops 派生）→ 省级汇总，不做单城联动
               is_loop=False 时本步不执行，省名也不得走省级
1  exact       原名精确                  → match_level=exact
2  base_equal  候选去后缀基名 == 输入基名 → match_level=normalized
               （多个基名等价命中          → found=False + 候选列表，先查后问）
3  alias       县级市别名表              → match_level=alias（标注精度降级）
4  municipality 直辖市区县              → match_level=municipality（标注精度降级）
5  substring   子串兜底：带省份时只接受同省候选；不带省份且属跨省歧义简称 → 列候选
               同省唯一命中              → match_level=normalized
               多命中                    → found=False + 候选列表（先查后问）
6  none        全部失败                  → found=False + 「fun 库未覆盖此城」
```

**归一化顺序**：`自治州 → 地区 → 盟 → 市 → 区`（长后缀优先，避免「自治州」被「区」误截）。

**第 2 步为什么用「基名等价」而不是「子串包含」**：子串会把 `鞍山` 命中到 `马鞍山市`。
基名等价要求 `normalize_city(候选) == normalize_city(输入)`，`马鞍山市 -> 马鞍山 != 鞍山`，自动排除。
宽松子串仅作为第 5 步兜底，且多命中一律报歧义。

**第 5 步为什么加省份硬闸**：全量扫描 29 个「子串兜底」命中中，28 个是同省自治州简称→全称（正确），
唯独 `海南` 跨省：`moto` 里「海南」同时出现在海南省与青海省，fun 库只有青海「海南藏族自治州」。
旧版不带省份时静默挂到青海，标 `normalized` 冒充精确匹配。现规则：
带省份只接受同省候选（无同省则不采用，如实写未覆盖）；不带省份且属 `AMBIGUOUS_SHORT_NAMES` 则列候选让用户选定。

## 4. 数据口径红线

| 项 | 规则 |
|---|---|
| 长途环线 | `cs=computed`，算法生成，**不得称实测**；与市区周边短途分开口径 |
| `reviewed` | 改写自公开资料、逐条附来源，`srcs>0` 才可核验 |
| 坐标系 | moto 轨迹 GCJ-02；配其他 WGS-84 底图需转系 |
| 评分 / 人均 | 采集时快照，非实时价格，答复不得写成「当前价」 |
| POI 名称 | 只能来自数据集；查不到写「未覆盖」，**绝不编造** |
| 泛化建议 | 不得用「可以去当地菜市场 / 逛逛步行街」这类模板凑数 |

## 5. 已知缺口（坦诚标注）

1. fun 仅 389 城单城档案，县级市 / 乡镇无覆盖；`city` 路径（不带省份）49 个 moto 城市名无单城档案，在 `cascade` 路径下已由省级 / 直辖市 / 别名降级全部覆盖，**但降级即精度损失**。
2. 两端无共同主键（moto 无 adcode，fun 无 slug），仅靠城市中文名对齐；数据更新后需重跑匹配率扫描。
3. 长途环线只有省级汇总，无法给出沿途每一站的消费推荐。
4. 两个数据集均为静态快照，不含营业状态、排队、票价、天气。
5. `districts_top` 实测 703 条，`meta.schema` 写「最多 1000」，两者口径不矛盾但需以实测为准。
6. `AMBIGUOUS_SHORT_NAMES` 与 `CITY_ALIASES` 为人工确认表，数据更新后需复核（当前各 1 / 4 条）。

## 8. 景点与必吃数据补充规范（v0.2.25 新增 · 回应「如何补充景点与游玩方式」「如何提高准确与完整」）

### 8.1 poi.json 字段契约（权威）

`references/poi.json` 结构：`{ "poi": { "<城市中文名>": [ {<POI 对象>} ] } }`。每个 POI 对象字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 景点名；可用 ` · ` 分隔「主名 · 副标题」（如「袁家界峰林 · 云雾中的悬浮山」），渲染会自动取主名 |
| `tag` | 是 | 标签（免费 / 人文 / 自然 / 海景 / 古城 / 美食 / 节庆 / 科技 …），用于分组与兜底 |
| `desc` | 是 | 一句玩法说明（含真实耗时 / 看点），来自公开资料并附 `source` |
| `info` | 否 | 票务 / 装备等补充（🎫 / 🚡 等 emoji 前缀） |
| `source` | 是 | 数据来源（如「大理官方文旅 · 实测推荐」） |
| `zone` | 否 | 城市内片区（海西 / 海北 / 市区中轴 …），用于人本路由的跨区封顶与路程量化 |
| `play` | 是（v0.2.25） | **游玩方式（怎么玩）**：一句具体的玩法建议，如「环湖骑行或步行，才村/喜洲均设出入口」 |
| `arrival` | 是（v0.2.25） | **怎么去（到达方式）**：一句具体的到达方式，如「古城乘公交/打车约20-30分钟到才村码头」 |
| `tickets` / `booking` | 否 | 票务 / 预约提示 |

**补充一个景点**：在对应城市数组里追加一个对象，补齐上述字段即可；`_load_poi_db()` 与渲染层会自动透传 `play` / `arrival`，无需改脚本。

### 8.2 必吃数据契约（food_guide.json）

`references/food_guide.json` 顶层按**城市 slug** 为键，每个条目含 `city`（中文城市名，渲染按中文名索引）与 `dishes[]`。每条 dish：`n`（品类名）/ `why`（为什么值得）/ `price`（参考价区间）/ `slot`（餐段：早餐/正餐/小吃/夜宵）。

**红线**：`dishes` 只给**品类**，绝不写具体店名、摊位、餐厅；价格标注「参考 / 非实时」。未覆盖城市在渲染层给出诚实「未收录，请查本地老店/夜市」提示（绝不编造菜品）。

**补充一座城市的必吃**：新增一个 slug 键，填 `city` 与 3–5 条 `dishes` 即可。v0.2.25 已把覆盖从 12 城扩到 25 城（补齐全部 20 个 poi 城市，含 v0.2.25 第二波新增的武汉/长沙/岳麓山/岳阳/新疆）。

### 8.3 补充流程（四步，可审计）

1. **先查本地库**：`poi.json` / `food_guide.json` 是否已覆盖该城；优先增量补充，不重复造数据。
2. **改数据文件**：按 §8.1 / §8.2 契约追加，来源与 `source` 一并写（公开资料 + 实地实测最佳）。
3. **doctor 校验**：`python scripts/doctor.py` 必须 17/17，且 `references/*.json` 可解析条目达标。
4. **重建包**：`python tools/build_pack.py --out <包>.zip --verify`，字节可复核后再发布。

### 8.4 三红线（不可破）

- **不编造**：查不到的景点 / 菜品一律写「未覆盖」，绝不生成看似合理的假数据。
- **不指店**：必吃只到品类与参考价，不出现具体店名、摊位、导航锚点。
- **缺则标灰**：数据缺失在渲染层显式降级（如「未收录必吃清单」），不以模板凑数（如「逛逛菜市场/步行街」）。
